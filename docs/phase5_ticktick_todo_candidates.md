# Phase 5: TickTick入力用TODO候補JSON生成

この文書は、Phase 5で扱う `ticktick-task` 向けTODO候補JSON生成の方針を定義します。

Phase 5は、Discord雑文から直接TickTickへ登録するPhaseではありません。
Phase 2で分類されたトピックの中から、タスク候補になりそうな内容を抽出し、`ticktick-task` 側へ渡せる候補データを作るPhaseです。

## 1. 目的

Phase 5の目的は、Phase 2のトピック分類結果からTODO候補を抽出し、文脈と根拠を失わない形で `ticktick-task` 側へ渡すことです。

Discordに投稿された雑文は、そのままではTickTickに登録しにくい形をしています。

たとえば、以下のような情報が混ざります。

* 具体的なTODO
* 条件付きのTODO
* 大きすぎる行動目標
* 後で確認したいこと
* 記録として残すだけの内容
* 開発確認メモ
* 生活メモ
* 案件名や人名だけで文脈を補う必要がある内容

Phase 5では、これらをいきなりTickTickへ登録せず、`ticktick-task` 側で統合判定や人間確認を行える候補データに整えます。

レビュー時の判断材料として、Phase 5は所要時間候補を `estimatedMinutesCandidate` に入れることがあります。
これは正式な見積もりではなく、後続の `ticktick-task` 側レビューで上書き、削除、分解できます。

## 2. このPhaseの位置づけ

`memo-workflow` は、Phase 2の後に2つのルートへ分岐します。

```text
Phase 2: 原文維持のトピック分類
  ↓
分岐

Notionルート:
  Phase 3: Notion貼り付け用Markdown生成
  Phase 4: Notion API転記

TODO候補ルート:
  Phase 5: TickTick入力用TODO候補JSON生成
    ↓
  ticktick-task
```

Phase 5はTODO候補ルートの出口です。

`memo-workflow` 側では、TODO候補JSONの生成までを担当します。

TickTickへの登録、既存TickTickタスクとの統合判定、人間確認CSV、OK済み候補の反映、作業ブロック化、作業ブロック用タスク出力は、`ticktick-task` 側で扱います。

## 3. 入力

Phase 5の入力は、Phase 2が出力したトピック分類JSONです。

想定入力:

```text
outputs/topic_classification_YYYY-MM-DD.json
```

Phase 5では、主に以下の情報を参照します。

* トピックID
* トピックタイトル
* 文脈ラベル
* 文脈ラベルの確定状態
* category
* flags
* confidence
* 分類理由
* 元投稿ID
* 元投稿本文
* 投稿時刻
* 添付メタデータ

Phase 5では、Phase 2の原文を変更しません。
TODO候補化に必要な情報は、元投稿とは別の候補データとして追加します。

## 4. 出力

Phase 5の出力は、`ticktick-task` 側へ渡すTODO候補JSONです。

想定出力:

```text
outputs/ticktick_todo_candidates_YYYY-MM-DD.json
```

必要に応じて、人間確認用Markdownも出力します。

```text
outputs/ticktick_todo_candidates_YYYY-MM-DD.md
```

JSONは後続処理に渡す正本です。
Markdownは人間が確認するための派生表示です。

詳細なJSON項目、必須項目、値のバリデーション、サンプルJSONは、この文書では確定しません。
実装直前に、出力JSON仕様として別途定義します。

## 5. 抽出対象

Phase 5では、基本的に `task_hint` が付いたトピックをTODO候補抽出の中心にします。

候補抽出の中心条件は、元投稿から行動が読み取れることです。

Phase 5では、拾い漏れを減らすことを重視します。
多少広めにTODO候補を出し、不要なもの、粒度が合わないもの、文脈が違うものは後続の `ticktick-task` 側レビューで却下、編集、分解する前提にします。
ただし、根拠となる行動文がないものを無理にTODO候補化しません。

以下のような表現は、具体的な対象や目的が読み取れる場合、TODO候補として扱えます。

* やる
* 決める
* 考える
* 確認する
* 修正する
* 納品する
* アップロードする
* 時間を取る
* 連れて行く
* 伝えないといけない
* 買いたい
* 作らないといけない
* 掃除する
* 請求する
* 業者に出す
* 先にやる必要がある

「考える」「決める」「確認する」のような検討系の表現も、本人が今後やる必要のある行動として述べており、対象や目的が読み取れる場合はTODO候補に含めます。

候補の粒度が粗いことだけを理由に、`hold_candidate` へ寄せません。
行動が読み取れ、後続の `ticktick-task` 側レビューで編集、却下、分解できる候補は、`todo_candidate` として渡せます。

ただし、`task_hint` がない場合でも、以下のような情報が含まれるトピックは確認対象にできます。

* 日程、頻度、時間確保に関係する内容
* 費用、請求、見積、収入に関係する内容
* 病院、体調、ケアなど生活上の実行事項
* 案件名や文脈ラベルがあり、行動を示す表現がある内容
* AI分類の信頼度が低く、人間が確認した方がよい内容

`task_hint` が付いていないトピックをTODO候補に含める場合は、人間確認が必要な候補として扱います。
ただし、病院、体調、ケアなどの生活記録であっても、具体的な行動や必要性が読み取れない場合はTODO候補にしません。

1つの投稿やトピックに複数の箇条書きTODOが含まれる場合は、投稿全体を1候補に丸めず、原則として行動単位に分けます。
このとき、Phase 2のトピック全体に付いた `context_label` や `flags` を全候補へ無条件に継承しません。
各行の本文を見て、辞書照合できる文脈、費用関連、日程関連などを候補ごとに付け直します。

Phase 2で1つのDiscord投稿が複数トピックに分かれた場合も、同じ元投稿の同じ行動文は1回だけ候補化します。
複数トピックが同じ元投稿全体を参照していても、各トピックのタイトルや分類理由と関係がある行動文だけを候補化します。

例:

```text
やること
・講座Cの動画を編集して公開する
・株式会社Aの保存対応をする
・株式会社A関連で広告担当へ連絡する
・お金の計算をする
```

上記は、少なくとも4件の候補として扱います。
`株式会社A` が含まれる行だけに `株式会社A` の文脈を付け、他の行へ自動継承しません。

## 6. 抽出しないもの

以下は、原則としてTODO候補にしません。

* 単なる記録
* 感想
* 状況説明だけの投稿
* 迷いや困りごとの吐き出しだけの投稿
* 読み込み確認やテスト投稿
* 添付だけで内容が判断できない投稿
* すでに完了した行動の記録
* タスク化するには情報が不足している投稿

たとえば、「どうしよう」「どうしたらいいんだろう」「困った」「良くない」だけのように、感情や迷いはあるが、具体的な対象、行動、必要性が読み取れないものは、TODO候補として拾いません。

ただし、後で見直した方がよいものは、破棄せず確認用表示に残すことがあります。

## 7. 候補ステータス

Phase 5では、抽出した内容を最低限以下の3種類に分けます。

```text
todo_candidate
hold_candidate
non_todo
```

### todo_candidate

`todo_candidate` は、`ticktick-task` 側へTODO候補として渡せるものです。

目安は以下です。

* 具体的な行動がある
* 「考える」「決める」「確認する」などの検討系行動でも、対象や目的が読み取れる
* 文脈が分かる
* タスク名として読める
* 元投稿から根拠を追える
* `ticktick-task` 側の統合判定に渡せる
* 粒度が粗くても、後続レビューで編集、却下、分解できる

例:

```text
店舗Bのホームページを修正して納品する
コミュニティDの営業と集客で何ができるか考える
株式会社Aで、残すサイトを決めてもらう
```

### hold_candidate

`hold_candidate` は、行動がありそうだが、そのままTODO候補として扱うには人間判断が必要なものです。

目安は以下です。

* 人間の判断が必要
* 条件が満たされた後で実行する
* 文脈、対象、担当、登録可否が分からない
* 登録前に分解方針を決めないと混乱する
* 日程や頻度の確認が必要で、候補名だけでは扱いにくい
* タスク名にはできるが、そのまま登録すると曖昧
* 行動ではなく、迷い、感情、方針メモに近い

例:

```text
生活リズムが良くないのでどうするか考えたい
```

### non_todo

`non_todo` は、タスク候補として扱わないものです。

記録としてNotionルートで扱う可能性はありますが、TODO候補ルートでは登録候補にしません。

例:

```text
家族の移動記録
```

## 8. 文脈保持ルール

Discord雑文から抽出したTODO候補は、短い行動名だけにすると文脈が失われます。

Phase 5では、候補ごとに以下の情報をできるだけ引き継ぎます。

* `context_label`
* `topic_title`
* 元投稿ID
* 元投稿本文
* 根拠となる発言
* category
* flags

箇条書きから候補を分ける場合は、元投稿IDと元投稿本文を保持しつつ、`sourceText` には根拠となる行を入れます。
必要に応じて `sourceContext.extractionMode` などで、トピック全体由来か、行単位抽出かを区別できるようにします。

たとえば、以下のようなタイトルは避けます。

```text
残すサイトを決めてもらう
ホームページを修正する
確認する
アップロードする
```

以下のように、文脈が分かる候補名にします。

```text
株式会社Aで、残すサイトを決めてもらう
店舗Bのホームページを修正して納品する
コミュニティDの営業方法・できることを再確認する
講座Cの動画をアップロードする
```

ただし、本文にない情報をAIが勝手に補ってはいけません。
文脈は、Phase 2の `context_label`、`topic_title`、元投稿本文、辞書照合結果から引き継ぎます。

## 9. 人間確認の扱い

Phase 5では、候補ごとに人間確認が必要かどうかを判断できる形にします。

以下のような候補は、人間確認が必要です。

* 費用や請求判断が含まれる
* 条件付きで実行する
* 日程や頻度が曖昧
* 登録前に分解方針を決めないと混乱する
* 文脈ラベルが未確定
* AI分類の信頼度が低い
* 本文から判断しきれない
* タスク化するか記録に留めるか迷う

候補の粒度が粗いこと自体は、人間確認が必要な十分条件ではありません。
不要な候補、修正が必要な候補、分解が必要な候補は、後続の `ticktick-task` 側レビューで却下、編集、分解される前提とします。

人間確認が必要な候補には、確認が必要な理由を残します。

例:

```text
費用を上乗せ請求するかの判断が必要
マルウェア除去完了後に実行する条件付きタスク
行動目標として大きく、具体タスクへの分解が必要
```

## 10. blockingHint の扱い

Phase 5では、`ticktick-task` 側の作業ブロック分類に使える参考情報を付けることがあります。

この参考情報を `blockingHint` と呼びます。

`blockingHint` は、`ticktick-task` 側の正式な `classification` ではありません。

Phase 5では、以下のようなヒントを付けることがあります。

* 作業ブロック候補になりそう
* 人間確認が必要そう
* 分解が必要そう
* 所要時間見積もりが必要そう
* 条件待ち、後続確認になりそう
* 参考情報になりそう
* タスク化しない可能性が高い

正式な作業ブロック分類は、`ticktick-task` 側で行います。

## 11. AI利用の方針

Phase 5では、AIを使ってTODO候補抽出を行う可能性があります。

AIを使う場合も、以下を守ります。

* AIは候補案を返すだけにする
* ファイル保存はPythonスクリプト側で行う
* Discord、Notion、TickTickへの書き込みをAIに行わせない
* 元投稿本文を書き換えない
* 本文にない情報を補わない
* 候補タイトル、候補ステータス、確認要否、根拠を構造化して返す
* AI出力はPython側で検証する
* 検証できないAI出力は成功扱いしない

AI APIは、Phase仕様で許可され、かつ実行時に明示オプションが指定された場合だけ呼び出します。

## 12. ticktick-task との境界

Phase 5の出力は、`ticktick-task` 側の入力として扱います。

`memo-workflow` 側で行うこと:

* Phase 2 JSONを読む
* TODO候補を抽出する
* 文脈と根拠を保持する
* 候補ステータスを付ける
* 人間確認が必要な理由を残す
* 所要時間候補をレビュー用の初期値として付ける
* `ticktick-task` 向けTODO候補JSONを出力する

`ticktick-task` 側で行うこと:

* TODO候補JSONを受け取る
* 既存TickTickタスクと照合する
* 統合判定を行う
* 人間確認CSVを作る
* 候補を承認、却下、編集、保留、分解する
* 必要に応じて候補を差し戻し、再処理対象として扱う
* OK済み候補をTickTickへ反映する
* 作業ブロック分類を行う
* 作業ブロック用タスクを出力する

`memo-workflow` 側では、TickTick APIへの登録、更新、削除を行いません。
また、候補の承認、却下、編集、分解、差し戻し、確認画面の提供も `memo-workflow` 側では行いません。

## 13. このPhaseでやらないこと

Phase 5では、以下を行いません。

* TickTick APIへの登録
* TickTick APIへの更新
* TickTick APIへの削除
* 既存TickTickタスクとの統合判定
* 人間確認CSVの作成
* OK済み候補のTickTick反映
* TickTick未完了タスクの作業ブロック分類
* 作業ブロック用タスクのTickTick出力
* Googleカレンダー空き時間参照
* Notion貼り付け用Markdown生成
* Notion API転記
* Discordへの投稿、編集、削除
* 元投稿本文の書き換え

## 14. 完了条件

Phase 5は、以下を満たした時点で完了候補とします。

* Phase 2の分類JSONを入力として読める
* `task_hint` が付いたトピックを中心にTODO候補を抽出できる
* TODO候補が短いタスク名だけになっていない
* 文脈ラベル、トピック名、元投稿ID、根拠を引き継げる
* `todo_candidate`、`hold_candidate`、`non_todo` を区別できる
* 人間確認が必要な候補に確認理由を残せる
* 明示時間またはローカルルールから `estimatedMinutesCandidate` を出力できる
* `ticktick-task` 側へ渡すTODO候補JSONを出力できる
* `ticktick-task` 側の入力仕様と受け渡し確認ができる
* TickTick APIへの登録、更新、削除を行っていない
* Notionルートの処理を混ぜていない
* Discordへの投稿、編集、削除を行っていない
