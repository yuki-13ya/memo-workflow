# アプリ制作方針

このプロジェクトでは、Discordに投稿したメモを段階的に取得、整理し、後続処理へ渡せる形へ育てます。

`memo-workflow` は、Discord投稿を取得し、原文を維持したまま分類し、Notion向けの記録データと、`ticktick-task` 向けのTODO候補データへ分岐させる上流プロジェクトです。

初期段階では、機能を広げすぎず、Phase 1のDiscord投稿取得を小さく、安全に検証します。

## 1. 設計の基本姿勢

処理の責務を分け、後から人間が読んで修正できる構成を優先します。

Discord取得、日付抽出、出力整形、保存、ログ出力、Notion向け出力、`ticktick-task` 向けTODO候補出力は、それぞれ別の責務として扱います。

一時的な見た目合わせや場当たり的な処理よりも、入力、処理、出力、例外時の流れが追える設計を重視します。

新しい実装を追加する前に、`docs/system_design.md` で現在の作業位置を確認します。

ただし、毎回すべてを深掘りして読み直すのではなく、作業の影響範囲に応じて確認の深さを調整します。確認する文書は、まず `docs/document-index.md` を見出し索引として選びます。

- 軽微な修正、誤字修正、既存仕様内の小変更では、対象Phaseと入出力の位置だけを確認します。
- 外部API、AI利用、認証情報、出力形式、Phase境界に関わる場合は、該当箇所を深く確認します。
- 全体フロー、処理主体、データ受け渡しを変える場合は、`docs/system_design.md` を更新してから実装します。

設計図が粗い、または未解決事項が作業に直接関係する場合は、先に設計やイシューを更新してから実装します。

未解決事項が対象作業に関係しない場合は、存在するだけで作業を止めません。

## 2. 文書責務の基本ルール

文書は役割ごとに分け、1つの文書に現在地、詳細仕様、判断履歴を詰め込みません。

- README.mdは、プロジェクトの入口案内にします。
- `docs/development_roadmap.md` は、現在地とPhase境界を管理します。
- `docs/system_design.md` は、プロジェクト全体の設計図を管理します。
- `docs/issues.md` は、未解決事項、確認事項、判断待ちを管理します。
- Phase仕様書は、そのPhaseの目的、対象範囲、入力、出力、例外処理、完了条件を管理します。
- `docs/change-log.md` は、判断変更とその理由を記録します。
- `AGENTS.md` は、Codexの作業姿勢と作業時のルールを管理します。
- `docs/app_policy.md` は、プロジェクト全体の上位方針を管理します。

README.mdにPhase固有の詳細や一時的な状態を書きすぎると、Phase進行後に入口文書としての意味が弱くなります。

そのため、README.mdは参照先を示す役割に留め、変更されやすい情報はロードマップ、Phase仕様書、change-logに分けます。

ベースになる文書には、作業時点に依存する表現をなるべく残しません。

Phase境界を表す場合は、「このPhaseで作るもの」「このPhaseで作らないもの」として書き、後続Phaseで実装が進んでも文書の意味が壊れない形にします。

一時的な判断や、その時点の作業範囲は `docs/change-log.md` または対象Phase仕様書に記録します。

未解決事項、確認事項、判断待ちは `docs/issues.md` に集約します。

固定の仕様文書や全体設計には、未確定の詳細を混ぜ込まず、必要に応じて `docs/issues.md` への参照だけを置きます。

判断が確定した場合は、確定内容を該当する仕様書や設計図に反映し、判断理由と影響範囲を `docs/change-log.md` に残します。

## 3. Phase単位の進行

実装はPhase単位で進めます。

Phase 1では、Discordの指定チャンネルから指定日の投稿を読み取り専用で取得し、MarkdownとJSONに保存するところまでを対象にします。

Phase 2では、Phase 1の出力JSONを入力にし、投稿本文の原文を維持したままトピック分類します。

Phase 2の分類結果は、後続で2つのルートに分岐します。

- Notionルート
- TODO候補ルート

Notionルートでは、分類結果をNotionで見返しやすい形に整え、必要に応じてNotion API転記を扱います。

TODO候補ルートでは、Discord雑文からタスク候補になりそうな内容を抽出し、`ticktick-task` 側が受け取れるTODO候補JSONを生成します。

`memo-workflow` 側では、TickTick APIへの登録、更新、削除を行いません。

TickTickへの登録、既存TickTickタスクとの統合判定、人間確認CSV、OK済み候補の反映、作業ブロック化、作業ブロック用タスク出力は、`ticktick-task` 側の責務として扱います。

## 4. AI利用の方針

AIは、後続Phaseでの分類、要約、タスク候補抽出などに使う予定です。

Phase 1では、AIによる分類、要約、本文改変を行いません。Discordから取得した本文は原文を維持します。

AIを導入する場合は、AIが担当する範囲、アプリ側で確定する範囲、失敗時の扱い、人間の確認範囲を仕様に明記します。

AIは、分類案、抽出案、判断補助を返すだけです。

外部サービスへの保存、登録、更新、削除は、Pythonスクリプト側で制御します。

AIにNotionやTickTickへ直接書き込ませません。

AIプロンプトを作る場合は、禁止命令を中心に組み立てず、望ましい作業方法、出力単位、判断基準、根拠の扱いを肯定文で指示します。

具体例は、AIの出力を例文の語彙や構造へ引っ張ることがあります。
そのため、まず抽象的な型、判断基準、出力項目の説明で指示します。
例文は、抽象ルールだけでは誤解されやすい場合に限って最小限使います。

例文を入れる場合も、特定の案件名、生活場面、表現に寄りすぎないようにし、例文そのものを再現させる目的ではなく、判断の型を伝える目的で使います。
単一の例だけで出力を誘導しすぎる場合は、例を削るか、より抽象的な説明に戻します。

安全上どうしても避けたいことは、Python側の検証、スキーマ制約、外部書き込み禁止、認証情報管理で担保します。
プロンプトでは、AIに望ましい作業へ集中させ、禁止事項の列挙は最小限にします。

## 5. 処理主体の統一方針

Phaseごとに処理主体がばらばらにならないように、役割を以下のように分けます。

| 主体 | 役割 |
|---|---|
| Codex | 開発支援、仕様整理、コード作成、検証支援。実行時の分類エンジンや外部API操作主体にはしない |
| Pythonスクリプト | ファイル読み書き、辞書照合、ログ出力、Discord / Notionなど外部API操作の実行主体 |
| 実行時AI | トピック分類、タスク候補抽出など、文章判断が必要な箇所で使う。Phase 2ではGeminiを第一候補にする |
| 人間 | 辞書、カテゴリ、要確認項目、最終的な運用判断を管理する |
| ticktick-task | TickTickへの登録、既存TickTickタスクとの統合判定、人間確認CSV、OK済み候補の反映、作業ブロック化を扱う別プロジェクト |

外部サービスへの読み書きは、AIに直接任せず、Pythonスクリプト側で行います。

AIは分類案、抽出案、判断補助を返すだけとし、保存、登録、更新、削除などの状態変更はアプリ側で制御します。

`memo-workflow` 側のPythonスクリプトは、Discord読み取り、ファイル保存、分類前処理、Notion向け出力、`ticktick-task` 向けTODO候補JSON生成を担当します。

TickTick APIへの登録、更新、削除は `memo-workflow` 側のPythonスクリプトでは扱いません。

実行時AIを使うPhaseでは、プロバイダ、モデル、呼び出し方式、認証情報名をPhase仕様書で確定します。

別のAIプロバイダへ切り替える場合は、そのPhase仕様書と `docs/change-log.md` に、理由、影響範囲、切り替え条件を記録します。

辞書照合のようにルールで確定できる処理は、AIに渡す前にPython側で行います。

AI判断よりも、人間が管理する辞書、完全一致、明示ルールを優先します。

## 6. 外部連携の方針

外部サービス連携は、必要なPhaseで最小限から追加します。

Phase 1のDiscord連携は読み取り専用です。投稿、編集、削除、リアクション追加、チャンネル設定変更は行いません。

Notion API転記は、Notionルートの後続Phaseで扱います。

Notion API転記を行う場合は、対象データ、登録先、実行条件、DryRunまたは人間確認、ログ方針をPhase仕様書で定義します。

TODO候補ルートでは、`ticktick-task` 側へ渡すTODO候補JSONを生成します。

`memo-workflow` 側で扱うTickTick向け処理は、`ticktick-task` 側へ渡すTODO候補JSONの生成までとします。

`memo-workflow` 側では、TickTick APIへの登録、更新、削除を行いません。

TickTickへの登録、既存TickTickタスクとの統合判定、人間確認CSV、OK済み候補の反映、作業ブロック化、作業ブロック用タスク出力は、`ticktick-task` 側の責務として扱います。

Phase 1では、Notion API転記とTODO候補JSON生成を実装しません。

## 7. 認証情報管理

Bot Tokenや秘密値は、コード、文書、ログ、出力ファイルに書きません。

必要な設定は環境変数から読みます。`.env.example` には環境変数名だけを記載し、実際の値は記載しません。

認証情報が不足している場合は、どの環境変数が不足しているかだけをログに出し、値そのものは出しません。

環境変数に認証情報が存在していても、それだけで外部AI APIや外部サービスへの書き込みを実行しません。

外部AI APIの呼び出し、Notion転記などは、Phase仕様で許可され、かつ実行時に明示オプションが指定された場合だけ行います。

`memo-workflow` 側では、TickTick APIへの登録、更新、削除を行わないため、TickTick書き込み用の認証情報を扱いません。

読み取り専用確認、DryRun、通常の分類前処理では、外部AI APIを呼びません。

実行ログや出力には、外部AI APIを呼んだか、呼ばなかったかを分かる形で残します。

## 8. ログ方針

ログは、失敗時に原因を切り分けられる粒度で残します。

Phase 1では、少なくとも以下の段階を区別します。

- 環境変数の読み込み
- Discord認証
- チャンネル取得
- メッセージ取得
- Asia/Tokyo基準の日付抽出
- Markdown / JSON 出力保存

後続Phaseでは、以下も必要に応じて区別します。

- 入力JSON読み込み
- 辞書照合
- AI呼び出し有無
- AI出力検証
- Notion向け出力生成
- Notion API転記
- `ticktick-task` 向けTODO候補JSON生成
- 出力保存

ログには、認証情報やトークンを出しません。必要以上に投稿本文をログへ出すことも避けます。

`ticktick-task` 向けTODO候補JSON生成では、元投稿ID、対象日、候補件数、警告件数など、受け渡し確認に必要な情報をログに残します。

TickTick APIへの登録、更新、削除のログは `memo-workflow` 側では扱いません。

## 9. 出力管理

取得結果は `outputs/` に保存します。

ログは `logs/` に保存します。

出力ファイルとログは、検証や運用確認のためのローカル成果物として扱い、認証情報や秘密値を含めません。

主な出力は以下のように扱います。

| 出力 | 役割 |
|---|---|
| `outputs/discord_messages_YYYY-MM-DD.json` | Discordから取得した原文と添付情報 |
| `outputs/topic_classification_YYYY-MM-DD.json` | Phase 2の分類結果 |
| `outputs/notion_markdown_YYYY-MM-DD.md` | Notion貼り付け用Markdown |
| `outputs/ticktick_todo_candidates_YYYY-MM-DD.json` | `ticktick-task` 側へ渡すTODO候補JSON |

Phase 2の分類結果は、NotionルートとTODO候補ルートの共通入力として扱います。

Notion向け出力と `ticktick-task` 向けTODO候補JSONは、別の出口として扱います。

## 10. 実装状況と確認状況の区別

コードや文書が存在するだけでは、実環境で確認済みとは扱いません。

報告や仕様書では、以下を分けて記録します。

- 実装済み
- 実データで確認済み
- テストデータで確認済み
- 未確認
- 未実装

後続Phaseは、未確認の機能を動作済みの前提にしません。

Notion API転記や `ticktick-task` 向けTODO候補JSON生成も、実装済み、実データ確認済み、テストデータ確認済み、未確認、未実装を分けて扱います。

`ticktick-task` 側で行う処理は、`memo-workflow` 側の確認済み機能として扱いません。

## 11. Git運用

Gitの具体的な運用ルールは `AGENTS.md` の「Git運用ルール」に従います。

Codexによる作業では、1つの作業単位が完了するたびに差分確認とコミットを行い、未コミットの変更を残したまま次の大きな作業へ進みません。
